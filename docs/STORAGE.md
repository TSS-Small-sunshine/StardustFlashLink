# 存储选型备查：配置 / 密码 / 历史，该不该用 SQLite？

> **状态：暂不实施（2026-09-29 讨论记录）** ✓ —— 记在这里是为了下次有人（或我自己）
> 再冒「要不要上 SQLite」的念头时，不必重新推一遍 ✓。
>
> **结论先写在这** ✓：
> 1. **配置与密码继续用 `config.json` / `password.txt`** ✓ —— 不上 SQLite ✗；
> 2. **历史与指标若要长期保留，优先上 JSONL 事件日志** ✓ —— 而不是 SQLite ✓；
> 3. SQLite 只在「确实需要 SQL 式查询」时才考虑 ✓，且**只在 2.x 侧**（Python 标准库自带 `sqlite3` ✓）；
>    3.0 侧仍守零依赖 ✓（不引 `rusqlite` ✗），两边用同一套 JSONL 格式 ✓。

---

## 1. 当时的事实核查（不是拍脑袋 ✓）

| 事实 | 依据 |
| --- | --- |
| 2.x 代码里**没有任何 sqlite 痕迹** ✓（全新建 ✓） | 全仓 `Select-String 'sqlite'` → 0 命中 ✓ |
| 2.x 安装器是**整目录**打包内嵌 Python ✓ | `packaging/setup.iss`：`Source: "..\python\*"; DestDir: "{app}\python"; recursesubdirs` ✓ |
| 官方 embeddable 包**自带** `_sqlite3.pyd` + `sqlite3.dll` ✓ | python.org `python-3.12.x-embed-amd64.zip` 的常规内容 ✓（**要用就先真机验一行**：`python\python.exe -c "import sqlite3; print(sqlite3.sqlite_version)"` ✓） |
| 所以 2.x 上 SQLite 的**依赖成本 ≈ 0** ✓（标准库 + 无需改打包 ✓） | 同上 ✓ |
| 3.0（Rust）上 SQLite 的**成本很高** ✗ | `rusqlite` 是第三方 crate + 捆绑 C 库 ✗ → 撞 **R1 零功能型依赖** ✓；6 个目标（含 armv7/aarch64 交叉）都要链接 ✓；体积 +1MB 量级 ✓ |
| 现在的**指标是从日志现算**的 ✓ | 2.x v2.0.8.0 的设计：「不落第二份状态文件 → 重启不清零、升级不丢」✓ |

---

## 2. 为什么这要分成两件事谈 ✓

**「配置」和「历史」的取舍完全不一样** ✓ —— 混在一起谈就会得出错误结论 ✗。

### 2.1 配置 / 密码：**不该**上 SQLite ✗

| 理由 | 说明 |
| --- | --- |
| **向后兼容契约** | `config.json` / `password.txt` 是 2.x 的兼容承诺 ✓（AGENTS 不变量 I8：安装时 `onlyifdoesntexist`、升级**不得覆盖**用户数据 ✓；老用户零迁移 ✓） |
| **人可读、可手改、可拷走** | 出问题时让用户「打开 config.json 看一眼」是**支持成本最低**的路径 ✓；二进制 db 做不到 ✗ |
| **脱敏/导出全建立在「文本」上** | 诊断包脱敏 ✓、配置导入导出 zip ✓、隐私守卫（拿真机文件内容去比对入库文件 ✓）—— 全是文本级能力 ✓，搬进 db 要全部重做 ✗ |
| **量级根本不需要** | 方案上限 12 个 ✓、字段十来个 ✓ —— JSON 是**恰好**的数据结构 ✓ |

### 2.2 历史 / 指标：**有真实收益，但有更便宜的解法** ⚠️

**SQLite 能给的** ✓：结构化事件 ✓ 任意时间窗查询 ✓ 事务与索引 ✓ 长期保留 ✓ 多进程并发写更省心 ✓。

**代价（必须先想清楚 ✗）**：

1. **多出一份状态** ✗ —— 现在指标是从日志现算的 ✓；引入 db 后要处理「db 与日志不一致」（谁为准？坏了怎么补？）✓
2. **`history.db` 不能进诊断包** ✗ —— 要么整包排除 ✓，要么先导出文本再走现有文本级脱敏 ✓
3. **升级不得覆盖** ✓（I8 同款要求 ✓）+ 要进 `.gitignore` ✓（`history.db*`、`-wal`、`-shm` ✓）
4. **必须优雅降级** ✓ —— db 损坏 / 被删 / 被锁：服务照常跑、面板显示空指标、**绝不 500** ✓（照抄 `metrics` 模块的降级哲学 ✓）
5. **3.0 侧会破 R1** ✗（或两边格式分叉 ✗）

---

## 3. 三个方案（按性价比排序 ✓）

### A（首选）JSONL 事件日志 ✓

一行一个 JSON 事件，**只追加** ✓：`logs/events.jsonl`

```json
{"ts":"2026-09-29T18:20:11+08:00","ev":"check","reason":"netwatch","online":true,"ms":812}
{"ts":"2026-09-29T18:41:03+08:00","ev":"profile","name":"教学楼","account":"2023000002","suffix":"@yd"}
```

- **零依赖** ✓（2.x 与 3.0 可以**共用同一格式** ✓✓）
- **纯文本** ✓ → 可读 ✓ 可 grep ✓ **可脱敏** ✓ 可进诊断包 ✓
- 长期保留 ✓（自己轮转 ✓）；统计时现算或一次性加载进内存 ✓
  （量级估算：一天几十~几百条事件 ✓ → 一年几万条 ✓ 完全够 ✓）
- 唯一不如 SQLite 的：复杂 SQL 查询与海量索引 ✗ —— 我们这个场景用不到 ✓

### B（需要 SQL 时）只在 2.x 用 SQLite 存事件 ⚠️

- 2.x 成本低 ✓（`sqlite3` 标准库 ✓、无需改打包 ✓）
- 但上面第 2.2 节那 5 条防护**一条都不能少** ✓
- 3.0 **不跟** ✓（守零依赖 ✓，仍写 JSONL ✓）；2.x 可选地把 JSONL **导入** db ✓ → 兼得 ✓

### C（不建议 ✗）配置也搬进 SQLite

兼容契约 ✓、可读性 ✓、脱敏与导入导出 ✓ 三重损失 ✗ —— 收益为零 ✗。

---

## 4. 什么时候值得回头做（触发条件 ✓）

出现下面任一情况，再回来把 B 拿出来评估 ✓：

1. **日志轮转导致统计缺口**变成真实抱怨 ✓（「上周的在线率查不到了」✓）—— 那时**先做 A** ✓；
2. 需要**按时间段 / 按方案 / 按账号**做交叉查询 ✓，且 A 的现算明显不够快 ✓；
3. 事件量级涨到**百万条**以上 ✓（例如开始记每次探测的明细 ✓）；
4. 真的出现**多进程并发写状态**的冲突事故 ✓（先做并发审计 ✓，多半是锁粒度问题 ✗，不是存储形式问题 ✓）。

---

## 5. 真要实施时的动作清单（2.x / B 方案 ✓）

1. 新建**版本分支**（例如 `v2.1.2.0` ✓）—— 不许塞进别的版本的 PR ✗
2. `.gitignore` 加 `history.db*` ✓
3. 诊断包 / 配置导出：**排除** db ✓，或导出为文本再走现有脱敏 ✓
4. 安装器：db 文件 `onlyifdoesntexist` ✓（I8 同款 ✓）
5. 全链路降级 ✓：打开失败 / 写入失败 / 损坏 → 记一行日志 ✓，功能照常 ✓，接口不 500 ✗
6. 冒烟断言落在**行为**上 ✓：db 被删掉后服务仍能跑 ✓、db 损坏后接口仍返回 200 + 空指标 ✓、诊断包里没有 db 条目 ✓
